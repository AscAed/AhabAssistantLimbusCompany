# Target Architecture and Optimization Decisions

Status: proposals, not implemented behavior. Baseline and evidence: [documentation investigation](../audits/2026-11-12-documentation-baseline.md), [current architecture](overview.md), [self-audit](../audits/2026-11-12-self-audit.md), and the versioned [AALC](../references/aalc.md) / [LALC](../references/lalc.md) reviews. Priorities indicate proposed ordering, not a claim that an incident has occurred.

## Architecture and Interfaces

Retain Windows, Python 3.12, PySide6, the locked environment and existing module boundaries as the starting point. The intended flow is:

`UI request -> preflight -> task worker/orchestrator -> game workflow -> capture/recognition and input ports -> Windows or simulator backend`

Configuration, logging, resource synchronization and updating remain services outside game-specific decisions. The UI owns user confirmation, progress, errors and lifecycle; workers own execution and cooperative stop; workflows own game state and decisions; automation owns capture, recognition and input; platform backends own native resources and coordinate translation. Resource and update services own their filesystem roots, with a user-visible plan and recoverable application.

Proposed internal contracts should be introduced incrementally at existing boundaries, not as a mandatory framework rewrite:

- A task has one terminal outcome: completed, failed with a reason, or cancelled. A cancellation request is distinct from confirmed worker termination; synchronous native calls remain bounded only where the underlying API supports it.
- Capture and recognition distinguish image/result, valid no-match, cancellation and execution failure. A result should identify the frame and coordinate space used, so a later input is not silently based on a stale frame.
- An input action reports delivery failure and restores acquired window state; each workflow establishes a state-based deadline, retry limit and safe failure exit. No implicit guarantee of actual game acceptance follows from an input call.
- Config changes are schema-validated and migrations preserve user values; persistence and shutdown completion have explicit error reporting. Resource changes enumerate managed paths and use containment, integrity checks and a documented recovery boundary.
- Extension points are existing backend and task interfaces. Add a smaller port only when a concrete test or second implementation demonstrates the need; keep Qt signals and platform specifics out of game decision logic where practical.

## Reference Decisions and Constraints

AALC's typed configuration, resource plan and Qt worker separation fit the existing stack; its direct writes, long loops and reference cancellation behavior are not copied as reliability guarantees. LALC's node graph, preflight and request correlation inform possible contracts, but its executor cancellation and heartbeat limitations require independent design. Both local references include AGPLv3 license files; verify provenance and obligations before copying code.

Do not design detection evasion, impersonation, packet tampering, security bypass or randomization intended to defeat auditing. Reliability work is limited to legitimate input, diagnosis, bounded operations, user control and avoiding unnecessary actions. A performance proposal must demonstrate correctness before reducing delays or retries.
