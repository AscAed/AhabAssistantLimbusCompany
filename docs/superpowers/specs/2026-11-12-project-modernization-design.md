## 意图

为当前 AALC 维护 Fork 建立一套可由 Codex 和其他维护者稳定使用的事实、审计、开发与验证体系。基于指定的本地 AALC 和 LALC 检出分析可复用的工程做法与可靠性风险；据当前 Fork 的源码、测试、日志、构建配置和可观察运行状态开展自检；修复有证据支持的问题，逐项清理已证明弃用或不兼容的内容，并将最终状态整理为可复查的提交。

项目服务对象是需要维护 Windows Python 桌面自动化程序的开发者与 AI 代理。优先保证任务可停止、识别失败可诊断、输入状态可恢复、用户配置与资源安全。

## 目标

- 建立简洁的根级 `AGENTS.md` 工作入口和 `docs/INDEX.md` 文档导航，声明唯一事实源、证据等级、更新规则和安全边界。
- 对本地参考检出做有版本标识的实现分析，不把其代码或历史说明直接当作当前 Fork 的事实。
- 复核当前 Fork 的源码、测试、依赖、配置、CI、打包、资源更新、日志和本地运行/制品身份；将发现分成已证实、待复现、环境限制和未覆盖。
- 修复复核确认且属于本次范围的问题，补充有针对性的离线回归验证。
- 对弃用和不兼容候选逐项检查代码引用、入口、打包/运行依赖、替代实现、测试与 Git 历史后再决定保留、迁移或删除。
- 清理重复、过时或相互矛盾的文档，同时保留有价值的历史证据和可追溯关系。
- 运行适用的语法、测试、Lint 和打包检查；形成只包含已验证结论的本地提交，并说明未关闭的验收项。

## 非目标与禁止项

- 不以绕过游戏检测或安全审计为目标；不实现行为伪装、反检测、封包篡改、客户端进程或内存绕过、驱动级规避或削弱安全控制的功能。
- 不把 AALC 或 LALC 的框架整体移植到本项目；只在代码证据、依赖成本、许可证和本地架构允许时借用具体设计。
- 不把历史日志、旧审计报告、CI 配置或静态检查结果描述成当前运行、真实游戏兼容或发布制品证明。
- 不覆盖或丢弃现有未提交用户改动，不读取、发布或提交个人配置、凭据、运行数据和未经脱敏的日志。
- 不以“自检完成”掩盖只能在用户桌面、真实游戏、真实设备或远端环境中验证的项目。

## 方案

1. **分阶段完成全目标（当前规划方案）**：冻结身份和工作区证据；完成参考项目和当前 Fork 分析；建立文档入口与事实文档；修复确认问题并测试；按证据清理；整理历史文档；执行最终验证并提交。每一阶段输出可审查证据，减少大范围变更的回归风险。
2. **先交付只读基线**：先完成比较分析、自检与文档结构，待审阅后再启动源码修复和环境清理。变更风险更低，但会将用户请求中的修复与提交推迟到后续批次。

采用方案 1 作为本次工作的默认规划路线；具体变更仍受本设计审批和每项证据门槛约束。

## 设计决策

- 将根级 `AGENTS.md` 保留为 Codex/代理的工作入口，不新增内容重复的 `Agent.md` 别名文件。
- 文档分为入口导航、当前项目事实、架构边界、参考实现分析、自检结果、开发/验证操作和历史记录。每个状态只指定一个权威来源；其他文档链接到该来源。
- 参考分析记录检出 SHA、标签、分析范围、路径/行号、可借用内容、风险和适用条件。建议以“是否值得借用、需要哪些适配与测试”为结论，而非按语言或代码量简单排名。
- 自检记录使用证据等级：源码/测试可确认、当前运行或制品确认、历史日志、静态假设、未验证。结论须注明时间、命令或观察来源。
- 清理必须先有逐项候选表，至少记录路径、当前引用、运行/打包入口、替代关系、测试影响、决定和验证结果。引用不明或运行身份不明的项目保留并登记。
- 对本地运行中的 AALC 进程不发送输入、不关闭、不更新；先尝试只读确认进程路径与制品对应关系。无法确认时，将运行状态记作“观察到进程，身份未证实”。
- 真实游戏交互仅在离线测试通过后评估；本批次不以未经授权的游戏操作作为验证手段。
- 提交前复核分支、工作区、差异、忽略文件、配置与日志边界。将审查确认属于本次目标且验证通过的既有用户改动一起整理；不自动推送或合并。只有验证完成且确有远程协作需要时，才准备 PR。

## 交付结构提案

- `AGENTS.md`：精简的项目操作规则、初始化顺序、安全边界与权威文档链接。
- `docs/INDEX.md`：文档导航、来源优先级和更新责任。
- `docs/PROJECT.md`：当前项目定位、平台/依赖契约、模块边界、支持状态。
- `docs/architecture/`：当前架构、关键数据/控制流、运行与资源更新边界。
- `docs/references/aalc.md`、`docs/references/lalc.md`：带提交身份的对比分析。
- `docs/audits/2026-11-12-self-audit.md`：当前自检结论、分级发现、证据、修复状态和剩余项。
- `docs/development/`：环境、测试、Lint、构建、日志与故障诊断操作。
- `docs/history/`：保留需要追溯的历史审计和方案，并标注其有效时间与是否被当前证据取代。

最终路径可依据现有引用和文档交叉链接调整；只有在确认链接与 Git 历史影响后才移动文件。

## 执行顺序

1. 记录三份仓库的分支、HEAD、标签、工作树状态和现有未提交差异。
2. 完成参考仓库分析及当前 Fork 的代码、测试、资源、CI、构建和运行身份审计。
3. 依据审计结果完成文档信息架构、候选清理清单与缺陷优先级。
4. 修复已确认的问题，先补离线回归用例，再做最小必要实现；每次变更独立复核。
5. 执行候选清理和文档重构，保留历史证据与源文件链接。
6. 执行全量验证、打包检查、差异与敏感数据复核，整理提交。

发现需要真实游戏/设备操作、外部授权、远端凭据，或可能损坏用户配置/证据的动作时，先完成可独立验证的工作，再说明具体缺口和影响。
